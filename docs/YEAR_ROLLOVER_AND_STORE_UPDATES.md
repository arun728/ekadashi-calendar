# Year rollover and store updates

Baseline audit of `dev` at `2d8f01b` and the approved implementation in draft PR #45.

## Baseline behavior on dev

- **Home (iOS and Android).** Both load all enabled years and use the Home city and tradition to select the first unfinished occurrence at launch, on a Home re-tap, and when the displayed current occurrence reaches Parana end. The Home list shows only one year and the automatic selection changes that year when necessary. The active Home re-tap keeps a fast visible through Parana. Returning from a different tab preserves its current card. Home's year menu lists 2026 then 2027.
- **Calendar.** Both support December and January within the same calendar, including the linked Parana entry on its actual local date. Calendar and Home share a concrete year in current code. Android observes changes to that year, while iOS uses the shared year when focusing Calendar and can set it when browsing months. A month/year wheel selects a concrete month and currently lists years oldest first.
- **Journey.** Overview, History, Statistics and Achievements use the shared Journey year menu. It already shows All years, then years descending, and supports history-only years. The underlying streak can span both years. The default year uses the device date, so test a device in a different year from the selected Home city around midnight.
- **Panchang.** Key days and Ekadashi browse a month. Daily, Muhurta and Rashi browse a day. All five share a date picker with a 1900–2100 range and use the Panchang location. The standalone Ekadashi calculation can already cross December into January. Key days also uses the Home occurrences for its Ekadashi entries.
- **Search and Settings.** Search already has All years followed by the enabled years in ascending order. Settings has no year scope menu. App reminders and native widgets receive the multi-year occurrence list and select from it. Test delivery around the boundary, including links to the right occurrence.
- **Update availability.** The Android production source is `1.1.1+4` and the audited `dev` snapshot is `2.0.0+5`. Neither has a Play in-app update client. The old Android `app_version` preference is local migration bookkeeping. Settings reads the installed version on both platforms. Native iOS has no store update check. The repository plans the first public iOS release alongside Android v2. Confirm the public version number and storefronts before enabling future version checks.

The shared fixture puts the Chennai Smarta cutoff at 08:42 IST on 21 December and its next fast on 3 January. Test the actual simulator/emulator timer and resume lifecycle before implementation sign-off.

## Year workflow

1. Default the Home, Search and Journey filters to the current civil year on both platforms. Use the Home city's date for the shared app calendar year. Show localized **All Years** first, then the available years newest first. The launch-era menu is All Years, 2027, 2026. All Years is an explicit choice and includes all available years. Keep manual filters while the user is browsing. When an automatically selected year rolls over, update it to the new current year.
2. On Home, start by showing current-year Ekadashis. The current/next card advances to the next enabled year as soon as the last local Parana ends, even if the calendar date is still in December. In the default flow, the selected year follows that card to January. Explicit All Years remains selected as its pager advances. Respect deliberate archive browsing. Retain the active Home re-tap's current/next rule across enabled years, including Parana. Returning from another tab restores the card last visible in Home.
3. Calendar opens on today's date in the Home city's year by default. Show newest year first in the year wheel and keep today's year initially selected. While the user is browsing, the wheel reflects the date being edited. Calendar Today returns to the current date. Keep its viewed date independent of automatic Home card rollover. Panchang's date picker and date range stay as they are.
4. Derive the year options from the enabled-year manifest as validated 2028, 2029 and 2030 ship. Journey keeps its history-only years. Exercise the end of the last shipped year so an old card can be recognized as archived. Preserve occurrence IDs, widget links, reminder deduplication, history and earned rewards.

## App update workflow

- **Android v1 to v2 at launch.** Rehearse Play Console's Recovery tools for the v1 production bundle. The read-only Play API confirmed a production v1 bundle and an internal v2 release. Google can show a full-screen, dismissible update when targeted users launch an already-published v1. Acceptance lets Play install the latest compatible version. Dismissal allows use until the next cold launch. Verify bundle, signing and track eligibility once the compatible v2 release is available in production. Check staged rollout targeting and the recovery preview before launch action. If ineligible, an updater-enabled v1 bridge can offer the flexible flow to users who install that bridge before v2 becomes available. [Play Console recovery documentation](https://support.google.com/googleplay/android-developer/answer/13812041)
- **Android v2 and future releases.** Ship the official Play In-App Updates API in v2 via the Kotlin/Flutter bridge. Any older Android build with this client can receive a flexible update to a higher Play-delivered version. Check on launch and foreground. Show a translated, dismissible Update available notice when eligible and suppress a dismissed offer for that version during the app session. Update now opens Play's confirmation over the app. Users can keep using the app during download. Offer Restart to update when ready and recover a completed download after relaunch. Play installs and restarts the app. [Play implementation guide](https://developer.android.com/guide/playcore/in-app-updates/kotlin-java)
- **iOS future releases.** Ship a dismissible update prompt in the first App Store build and show it when a newer compatible public release is available in the user's storefront. Use a storefront-aware availability check with the real Apple app ID and numeric version comparison. Validate the installed OS is supported and treat missing or unavailable data as no prompt. Apple's public lookup takes the two-letter territory derived from the StoreKit storefront. It checks the listing ID and bundle identifier before comparing versions. Open the public App Store product page when the user chooses to update. Apple handles installation and auto-updates. The app has no public Play-style in-app binary install API. [Apple product page guidance](https://developer.apple.com/library/archive/qa/qa1629/_index.html) · [Apple lookup examples](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/LookupExamples.html) · [Apple phased release guidance](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases)
- **Update languages.** Write all app-owned prompt, button, status and error strings in English, Hindi, Tamil, Telugu, Gujarati and Bengali. Both stores support developer-authored listing metadata in these languages. The Play update API and Play recovery action expose no text or locale setting for their confirmation UI. Apple supplies the App Store UI. Verify the observed store language and accept English where the store supplies it. Check app and device language both matched and mismatched. [Play update options](https://developer.android.com/reference/com/google/android/play/core/appupdate/AppUpdateOptions) · [Play localization](https://support.google.com/googleplay/android-developer/answer/9844778) · [App Store localization](https://developer.apple.com/help/app-store-connect/reference/app-information/app-store-localizations/)
